# `rubix/frontend` — Rubix Agent Console

React/Vite SPA for the `rubix-agent` runtime. Talks to the agent over
HTTP via `@nube/rubix-client-ts`, which is generated from
`rubix/openapi.json`.

## Layout

This app is the lighthouse consumer for the `@nube/starter-ui-*`
packages in the parent workspace. It's structured so a multi-person
team can grow it without colliding:

```
rubix/frontend/
├─ index.html                     Vite entry; brand title only
├─ vite.config.ts                 Plugins (tanstack-router, tailwind v4, react)
├─ playwright.config.ts           e2e on port 5187
├─ tsconfig.json                  NodeNext + @/* → ./src/*
├─ e2e/                           Playwright suites (one feature per file)
└─ src/
   ├─ main.tsx                    React root + providers (Theme, i18n, Router, Query)
   ├─ routeTree.gen.ts            ← generated by tanstack/router-plugin; never hand-edit
   │

   │  ├─ __root.tsx               Shell layout (sidebar + header + outlet)
   │  ├─ index.tsx                Landing
   │  ├─ dashboard.tsx            Metrics + activity (uses @nube/starter-ui-dashboard)
   │  └─ settings.tsx             Theme/layout config drawer host
   │
   ├─ components/
   │  ├─ layout/                  ↳ Shell pieces (app-sidebar, header, nav-group, nav-user, team-switcher)
   │  ├─ theme/                   ↳ Theme provider + ConfigDrawer sections (appearance, layout, branding, advanced)
```

## Long-term conventions (please read before contributing)

- **Routes own composition; components own pixels.** Routes wire data
  to components. Components never call `useNavigate`, never `fetch`.
- **Default to packages.** If you find yourself writing a sidebar, a
  metric card, a config drawer section, or a locale picker, check
  `@nube/starter-ui-*` first — it's probably already there. New
  app-local components live in `src/components/` only while they fail
  the [extraction bar](../../packages/README.md#extraction-bar-when-a-feature-graduates-from-examples).
- **i18n at the call site.** Every visible string flows through
  `useIntl().formatMessage({ id })`. No hard-coded English in JSX.
- **Theme tokens, not hex.** Use `bg-card`, `text-muted-foreground`,
  `border-border` from the shadcn surface. App-specific accents live
  in `src/styles/tokens.css` as `--rubix-*` variables.
- **No `@/*` imports inside `packages/`.** The CI guard
  (`scripts/check-no-alias-imports.mjs`) only inspects published
  packages, so the alias is fine here — but if you graduate a
  component into `@nube/rubix-ui-*`, rewrite to relative paths first.
- **HTTP through one client.** `RubixClient` from
  `@nube/rubix-client-ts` is the only allowed transport. Don't reach
  for `fetch` directly; add an endpoint module instead.

## Talking to rubix-agent

The dev server proxies `/api/v1` and `/openapi.json` to
`http://127.0.0.1:8088` (see `vite.config.ts`), so `RubixClient` uses
same-origin paths and bypasses CORS in dev. Construct it once via
`getRubixClient()` in `src/lib/client.ts`.

`VITE_RUBIX_BASE_URL` (Vite env var, baked at build time) overrides
the base URL — set it to a fully-qualified URL when the agent is on
a non-default port, behind a different host, or in production:

```bash
# Dev against an agent on a non-default port:
VITE_RUBIX_BASE_URL=http://127.0.0.1:9090 pnpm dev

# Prod build pointing at a deployed agent:
VITE_RUBIX_BASE_URL=https://rubix.example.com pnpm build
```

When unset (the default), the variable is empty and the client issues
relative requests that the Vite proxy (in dev) or the reverse proxy
hosting the SPA (in prod) is responsible for forwarding.
