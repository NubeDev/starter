Page 1 / Business and Domain View

From operational data to dashboards, reports, and alerts.

Rubix is the operator layer over the starter platform. It collects events, writes historical facts into ClickHouse, keeps dashboard definitions and permissions in Postgres, and uses SDUI so the same dashboard can render on web, mobile, and desktop shells.

Business reader

Think of Rubix as the workflow and dashboard system that turns raw operational signals into governed pages, weekly reports, and threshold-driven alerts.

Technical reader

The important split is simple: Postgres stores definitions and permissions; ClickHouse stores time-series history and marts; SDUI renders pages from typed JSON.

Looking for PLC or Node-RED style long-running jobs? Open Page 6: Runtime Flows for trigger → count → log, durable node state, live events, and hot-edit behavior.

How the parts come together

Sources Agents, extensions, scheduled checks, and external feeds produce facts.
Flows AI-agent flows call typed Rubix tools for dashboards, rules, reports, users, and system checks.
Warehouse ClickHouse stores raw history, curated rows, and query-ready marts.
Analytics Named SQL templates return rows for charts, KPIs, reports, and trend summaries.
SDUI Dashboard pages are typed component trees, not hand-coded screens.

The operating loop

Rubix is built around six operator goals. The same tool and flow pattern appears behind dashboards, flow programming, ClickHouse rules, system checks, user management, and analytics reports.

Warehouse

L1-L3

ClickHouse is the history store. Data lands as raw facts, becomes curated and tenanted, then turns into narrow marts that answer specific business questions quickly.

Analytics

SQL

Rubix uses named query templates such as weekly disk history, alert counts, flow run summaries, user activity, ClickHouse writes, and undo counts.

Dashboards

SDUI

Dashboards are saved as revisions of a ComponentTree. The server resolves data and permissions; renderers display the same page across clients.

Where tags fit

Tags are the vocabulary that lets people find and scope pages and data. The dedicated tags design doc is still a placeholder, but dashboard storage already reserves tags[] for filtering.

Business purpose

Tags give non-technical users a shared language: region, product, customer tier, host class, team, or dashboard purpose. They make "show me finance dashboards for APAC" possible without asking users to know table names.

region:apac team:ops system:clickhouse dashboard:weekly

System purpose

Tags act as metadata beside dashboard definitions and, later, broader rubix resources. They help list, filter, duplicate, and govern dashboards without changing the ClickHouse warehouse schema.

Implementation note: the tags README describes intent only. Treat tags as a planned/consumed starter-tags substrate, not as a completed standalone rubix system.

Page 2 / Developer Architecture View

The stack is a typed tool system with separate definition and history stores.

Rubix keeps a strict dependency arrow: starter-spi under rubix-spi; then rubix-tools, rubix-flows, rubix-skills, and rubix-client; finally rubix-agent wires the binary. Tools are exposed over MCP and HTTP without bespoke dashboard wiring.

Developer mental model

L1 raw
Ingest from agents, extensions, and feeds. Example: system_disk_history captures disk probes by tenant_id, host, percent used, free bytes, and epoch.
L2 curated
Rules convert raw rows into typed, deduplicated, tenant-aware data. This is the place for warehouse quality and retention discipline.
L3 marts
Small ClickHouse tables built for specific questions. Dashboard and report reads use L3 by default, with L2 allowed and L1 explicit.

Storage boundaries

The most useful implementation rule is knowing which store owns which kind of truth.

Postgres: definitions, control plane, permissions

dashboards_definitions Insert-only dashboard revisions: page_id, revision_id, body_json, tenant, owner, title, tags[], and supersede state.
flows_definitions Flow YAML revisions with pg_notify('rubix_flows_definitions', ...) so every agent reloads live flow revisions.
Authz resources Dashboard pages register resource specs. A denied view returns 404 to avoid leaking page existence.

ClickHouse: history, rules, marts

rubix database Rubix-owned ClickHouse tables live in the rubix database and should be qualified as rubix.<table> by operators.
Rule writer verbs rubix.clickhouse.rule.write, mart.create, and retention.set capture snapshots for undo-aware changes.
Tenant filter Tenancy is per-row tenant_id. Resolver-layer authz must apply the tenant filter on reads.

End-to-end control flow

The same pattern supports a user prompt, a scheduled report, or an extension-triggered workflow.

ai-agent node Skill-driven flow chooses allowed tools and emits structured tool calls.
rubix-tools Typed verbs implement starter_spi::tool::Tool and optional reversible changes.
Stores PG stores definitions and dashboard bodies. ClickHouse stores time-series history and marts.
Resolver/query SDUI resolve and analytics query bind user, page, target, and template parameters.
Renderer SduiPage renders the resolved ComponentTree and dispatches actions back through transport.

What each major piece owns

This is the quick reference for conversations between the developer and domain stakeholder.

Flow programmer

Deploys, duplicates, lints, and lists flow YAML. Deployed revisions notify every Rubix agent process, so the registry refreshes without an out-of-band reload RPC.

ClickHouse ruler

Writes rules, creates marts, and sets retention. Mutations are undo-aware by storing before/after snapshots through the changelog.

Analytics reporter

Runs named ClickHouse query templates, renders reports through starter-export, stores blobs, and records undo state for created report files.

SDUI tools

Create, get, update, list, duplicate, delete, history, and page_set manage dashboard pages. The AI builder uses page_set for full-tree writes.

Bindings

Bindings such as $target, $user, $page, $stack, and $msg connect the ComponentTree to live data, user context, page state, and localized text.

Extensions

Bundles can contribute tools, node kinds, skills, flows, and Module-Federation UI panels while staying behind the extension trait surface.

Page 3 / Data Flow, Databases, and Extensions

Postgres runs the control plane. ClickHouse runs the data plane.

Use this page when the conversation is specifically about how data enters Rubix, where it is stored, and how an extension can add new signals without becoming part of the Rubix core.

The two database split

Postgres

Stores definitions, revisions, permissions, schedules, extension metadata, and other control-plane records.

  • Dashboard pages and tags[]
  • Flow YAML revisions
  • Authz resource registrations
  • Scheduler and extension host metadata
ClickHouse

Stores high-volume history and analytics-ready marts in the rubix database.

  • L1 raw events and probes
  • L2 curated tenant-scoped rows
  • L3 marts for dashboards and reports
  • Retention rules and warehouse DDL

Focused data flow

The extension can bring in a signal, but the platform still decides what is metadata, what is history, and what is rendered.

1 Extension bundle A bundle under rubix/extensions/ declares tools, node kinds, skills, flows, and optional UI in block.yaml.
2 Tool or flow fires The extension handler returns structured data, or a flow node calls the extension as part of a scheduled or user-triggered workflow.
3A Postgres metadata Rubix stores definitions, page revisions, flow revisions, permissions, and tags. This is the governed catalog.
3B ClickHouse history Facts, probes, and events go to L1 raw history, then rules promote them to L2 curated rows and L3 marts.
4 Analytics query Named templates read ClickHouse marts with typed parameters instead of ad hoc SQL from dashboards.
5 SDUI dashboard The resolved ComponentTree uses Postgres page definitions and ClickHouse-backed data to render KPIs, charts, and tables.

Example extension: weather signal

This mirrors the extension guide's com.acme.weather example and shows what each contribution changes in the wider stack.

What the extension contributes

com.acme.weather.current tool Fetches current weather for a site, region, or asset group. The handler lives inside the extension process.
com.acme.weather.fetch node kind Lets a Rubix flow call the extension on a schedule or as part of a larger operational workflow.
Skill bundle Teaches the AI flow when to call the weather tool and how to describe the result to an operator.
Optional UI panel Ships a Module-Federation panel mounted under the extension slot for a purpose-built operator view.

What lands in Postgres

Extension identity, flow definitions that use the extension node, dashboard pages that display the weather signal, page tags such as source:weather, and authz resources for who can view or edit those pages.

What lands in ClickHouse

Historical weather observations, joined or correlated with operational events, promoted through L1/L2/L3 so dashboards can show trends like site temperature versus equipment alerts.

Decision guide

When explaining the architecture, this is the shortest way to decide where a new thing belongs.

Put it in Postgres when...

It describes a thing, controls access, tracks a revision, configures a flow, or helps users find a resource.

Put it in ClickHouse when...

It is historical, high-volume, time-based, aggregatable, or needs fast analytical reads across many rows.

Put it in an extension when...

The source system or UI is domain-specific and should plug into Rubix without changing Rubix core crates.

Page 4 / Tagging and ClickHouse Query Path

Analytical tags need to live where analytical queries run.

Rubix can keep tag vocabulary and dashboard page tags in Postgres, but anything used to filter time-series facts, marts, charts, and reports should be available inside ClickHouse. Otherwise every dashboard query becomes a two-database join in application code.

Current reality: the dedicated tags design doc is still a placeholder. Dashboard page tags already exist in Postgres for page listing. Warehouse docs already constrain analytical tag values to Bool and Str, which points toward a typed ClickHouse-friendly tag model.

Two tag roles

Catalog tags in Postgres

Used for governance and discovery of resources.

  • Dashboard list filters
  • Owner/team/resource metadata
  • Allowed vocabulary and labels
  • Authz-adjacent resource scoping
Analytical tags in ClickHouse

Used inside report and dashboard queries.

  • Fact row filters
  • Mart dimensions
  • Fast cohort/group-by queries
  • No PG pre-read on hot query path

Preferred query path

For dashboards and reports, the query API should bind tag filters directly into a ClickHouse template.

1 Dashboard filter User selects tags such as site:dc-1, asset:chiller, or critical:true.
2 rubix.analytics.query The resolver calls a named template and passes tag parameters through typed bindings.
3 ClickHouse template SQL filters on tags already present in the L2 table or L3 mart. No application-side PG join.
4 Rows returned The query returns chart/table/KPI rows that already reflect tenant, time, and tag filters.
5 SDUI render The page renders the filtered result and can refresh when the user changes tag selections.
PG Optional catalog read PG may populate tag picker options, but it should not be required for every analytical data read.

What not to do

This is the failure mode you called out: it adds latency, consistency risk, and app-level join logic.

Bad hot path

Dashboard asks PG for matching tagged resources, receives a list of ids, then asks ClickHouse for historical facts matching those ids. This turns every analytics query into a cross-store orchestration problem.

Better hot path

Ingest or mart rules copy the needed tag keys and values into ClickHouse. The dashboard sends tag_key / tag_value filters to rubix.analytics.query, and ClickHouse answers directly.

ClickHouse tag shapes

The exact schema belongs in the tags design doc, but the page should make the direction clear.

Raw event tags

L1 rows can carry incoming tags from agents/extensions. A flexible shape such as a string map works for ingestion, with indexes on keys and hot values where needed.

Curated typed tags

L2 should normalize allowed tag types to Bool and Str, matching the warehouse constraint and avoiding runtime type discovery.

Mart dimensions

L3 marts should promote the highest-value tags into direct dimensions when they are used constantly in dashboards, reports, or alert cohorts.

Concrete example

A weather extension or system probe can attach tags once during ingest, then every analytical consumer uses those tags from ClickHouse.

Ingest
Extension emits rowtenant_id, timestamp, measurement, and tags such as site, region, asset_type.
ClickHouse L1Stores the incoming fact and raw tag map in rubix.
Rule promotes rowNormalizes tag keys, validates allowed types, and writes L2.
Mart builds viewCopies hot tags to dimensions used by dashboards.
Query
Tag pickerOptions may come from PG vocabulary or a ClickHouse distinct query, depending on freshness needs.
Analytics templateBinds region and asset_type as query params.
ClickHouse filterApplies tenant, time window, and tag filters in one query plane.
Dashboard resultSDUI receives rows already scoped to the tag selection.

Design rule

The short version to carry into the actual tags design work.

PG is the catalog

Use Postgres to define tag names, labels, descriptions, ownership, allowed values, and page/resource metadata.

ClickHouse is the filter plane

Use ClickHouse for tags that filter facts, trends, reports, alerts, cohorts, and warehouse marts.

Sync is ingest-time

Copy or validate tags when data is written or promoted. Do not make every read query reconstruct tags from PG.

Page 5 / Flows, Nodes, and Tools

A flow is the recipe. Nodes are the steps. Tools are the actions.

The easiest mental model is: a flow describes what can happen, a node performs one part of that flow, and a tool is a callable operation such as listing dashboards, writing a ClickHouse rule, or deploying a new flow revision.

In the bundled Rubix goal flows, the root node is usually an ai-agent. That node receives a skill prompt plus an allowed_tools list. The agent can reason in text, but state changes still happen through typed tools.

Hierarchy

Flow
A versioned YAML definition such as com.rubix.dashboard-assistant or com.rubix.flow-programmer.
Node
A step inside the flow. Rubix goal flows commonly use one ai-agent node, but extensions can add new node kinds.
Tool
A typed callable operation implementing starter_spi::tool::Tool, exposed over MCP/HTTP and optionally undo-aware.

What happens when a user calls a goal

This is the path behind prompts like "build me a disk dashboard" or "deploy this flow".

1 User starts goal The user invokes a flow such as com.rubix.dashboard-assistant.
2 FlowAsTool The flow itself auto-surfaces as a callable MCP tool, so there is no bespoke MCP wiring per flow.
3 ai-agent node The node loads the skill, session policy, cost cap, and allowed tool list from the flow YAML.
4 Tool registry The agent can only call tools registered at boot and allowed by that node's config.
5 Typed tool call A concrete tool executes: dashboard write, flow deploy, ClickHouse rule, analytics query, or undo.
6 Result returned The flow returns a response, diagnostics, created resources, or a rendered dashboard/report path.

Dashboard assistant example

The flow is short because the behavior lives in the node, skill, and tools.

Flow YAML says

  • id: com.rubix.dashboard-assistant
  • trigger: explicit
  • one node: kind: ai-agent
  • skill_hint: com.rubix.dashboard-builder
  • allowed tools: rubix.dashboard.list, get, create, update, page_set, undo.last

Runtime behavior is

The AI node reads the skill, decides which dashboard operation is needed, calls one or more allowed tools, and returns a human-readable explanation. It does not directly mutate the database without a tool call.

Built-in tools vs extension tools

Both are tools from the caller's point of view, but they come from different places.

Built-in Rubix tools

Live in rubix-tools and implement the six product goals: dashboards, users, flow ops, ClickHouse rules, system checks, and analytics/reports.

rubix.dashboard.page_set rubix.flow_ops.deploy rubix.clickhouse.mart.create rubix.analytics.query

Extension tools and nodes

Declared by an extension block.yaml. Tools expose callable operations; node kinds let flows use extension behavior as a flow step.

com.acme.weather.current com.acme.weather.fetch skills/weather/SKILL.md ui/remoteEntry.js

Decision guide

Use this when deciding whether to add a flow, node, or tool.

Add a tool when...

You need one concrete operation with typed input/output: write a dashboard, query analytics, create a mart, or deploy a flow.

Add a flow when...

You need a user-facing workflow that combines reasoning, multiple tools, policy, and repeatable orchestration.

Add a node kind when...

You need reusable flow behavior that is not just one tool call, especially if an extension owns that behavior.

Short version: users call flows for outcomes; flows run nodes; AI-agent nodes choose from allowed tools; tools do the actual reads and writes; Postgres stores flow/dashboard definitions and revision state.
