Runtime Flows, Long-Running Jobs, and Live Nodes

Runtime flows are long-running graphs, not one-shot tool calls.

Use this model for PLC-style or Node-RED-style jobs: a trigger fires, values move through linked nodes, stateful nodes remember their last value, and operators watch slot values update live.

This is different from the AI/tool model. Tools manage the flow, deploy revisions, query status, and perform side effects. Runtime nodes keep running after boot and pass values through links.

Two execution models

Tool-driven flow

A user or AI asks for an outcome. The flow runs, calls tools, returns a result, then stops.

  • Dashboard assistant
  • Flow programmer
  • ClickHouse ruler
  • Analytics reporter
Runtime flow

A graph is mounted at boot. Triggers fire repeatedly and node state survives across runs.

  • Schedule or event trigger
  • Counter / transform / log nodes
  • Durable node state
  • Live canvas updates

Tick counter runtime example

The reference flow is com.rubix.tick-counter: schedule trigger -> counter -> log.

1 Mounted at boot The agent loads the YAML and registers the live flow revision.
2 Schedule trigger starter.flow.trigger.schedule fires every 5 seconds from cron */5 * * * * *.
3 Counter node starter.flow.counter reads prior count from NodeStateStore, adds step, and writes it back.
4 Log node starter.flow.log records the value and passes the latest slot value to subscribers.
5 Live canvas SSE events update the canvas with latest node status and slot values.
6 Hot edit Changing step from 1 to 10 updates the next tick without restarting the agent.

Runtime state and events

Long-running flows need state, event streaming, and safe redeploy behavior.

NodeStateStore

Stores per-node values under (flow_id, node_id, key). The counter uses it so a restart does not reset the count.

Flow events

GET /api/v1/flows/{flow_id}/events streams node start, emit, and failure events for live operator views.

Hot reload

Settings changes can affect the next tick. Topology changes swap the graph for future runs while in-flight runs finish on their current snapshot.

PLC / Node-RED style mental model

Think of the runtime as scan/tick/event-driven node execution with visible wires.

Where tools still fit

Even in a long-running runtime, tools remain the controlled operations around the graph.

Deploy and edit

rubix.flow_ops.deploy writes a new flow revision. Hot-edit uses the same safe deploy path.

Inspect and list

rubix.flow_ops.list and flow event routes show what exists and what is currently running.

Undo changes

rubix.undo.last can roll back a deployed flow revision when the change was reversible.
