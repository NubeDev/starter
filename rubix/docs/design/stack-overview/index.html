Business and Domain View

From operational data to dashboards, reports, and alerts.

Rubix is the operator layer over the starter platform. It collects events, writes historical facts into TimescaleDB, keeps dashboard definitions and permissions in Postgres, and uses SDUI so the same dashboard can render on web, mobile, and desktop shells.

Business reader

Think of Rubix as the workflow and dashboard system that turns raw operational signals into governed pages, weekly reports, and threshold-driven alerts.

Technical reader

The important split is simple: Postgres stores definitions and permissions; TimescaleDB stores time-series history and marts; SDUI renders pages from typed JSON.

How the parts come together

Sources Agents, extensions, scheduled checks, and external feeds produce facts.
Flows AI-agent flows call typed Rubix tools for dashboards, rules, reports, users, and system checks.
Warehouse TimescaleDB stores raw history, curated rows, and query-ready marts.
Analytics Named SQL templates return rows for charts, KPIs, reports, and trend summaries.
SDUI Dashboard pages are typed component trees, not hand-coded screens.

The operating loop

Rubix is built around six operator goals. The same tool and flow pattern appears behind dashboards, flow programming, TimescaleDB rules, system checks, user management, and analytics reports.

Warehouse

L1-L3

TimescaleDB is the history store. Data lands as raw facts, becomes curated and tenanted, then turns into narrow marts that answer specific business questions quickly.

Analytics

SQL

Rubix uses named query templates such as weekly disk history, alert counts, flow run summaries, user activity, TimescaleDB writes, and undo counts.

Dashboards

SDUI

Dashboards are saved as revisions of a ComponentTree. The server resolves data and permissions; renderers display the same page across clients.

Where tags fit

Tags are the vocabulary that lets people find and scope pages and data. The dedicated tags design doc is still a placeholder, but dashboard storage already reserves tags[] for filtering.

Business purpose

Tags give non-technical users a shared language: region, product, customer tier, host class, team, or dashboard purpose. They make "show me finance dashboards for APAC" possible without asking users to know table names.

region:apac team:ops system:tsdb dashboard:weekly

System purpose

Tags act as metadata beside dashboard definitions and, later, broader rubix resources. They help list, filter, duplicate, and govern dashboards without changing the TimescaleDB warehouse schema.

Implementation note: the tags README describes intent only. Treat tags as a planned/consumed starter-tags substrate, not as a completed standalone rubix system.

Data to dashboard flow

This is the plain-language path from a measurement or event to something a user can act on.

1. Collect
System probeExample: disk usage returns percent used and free bytes.
ExtensionsExternal systems can contribute tools, node kinds, skills, flows, and UI panels.
Scheduled flowsWeekly jobs or health checks fire without a human prompt.
Operator actionA person asks the AI flow to create or update a dashboard.
2. Store
TimescaleDB L1Raw history, short retention, one row per fact.
TimescaleDB L2Curated, typed, deduplicated, tenant-scoped rows.
TimescaleDB L3Marts designed for fast reads by dashboards and reports.
PostgresDashboard definitions, flow definitions, authz resources, and revisions.
3. Present
Analytics queryNamed SQL templates read TimescaleDB with typed parameters.
ReportRows render to HTML, CSV, or JSON and are stored as blobs.
InsightThreshold checks can dispatch alerts after tool results.
DashboardSDUI resolves a typed page and renders KPIs, charts, tables, and actions.
