SDUI — Server-Driven UI

One page definition. Web, mobile, and desktop render it the same.

SDUI lets operators and the dashboard-assistant AI flow author a single dashboard tree that renders identically across the React web shell, the Flutter mobile app, and the Tauri desktop wrapper — with no per-platform widget code. The server stores the definition, resolves the data, and ships a typed ComponentTree. The client just walks the tree and draws.

Where the pieces live

Postgres

Source of truth for the page definition — the unresolved tree.

  • dashboards_definitions rows
  • Per-page revisions + NOTIFY on write
  • Authz registration as a resource
TimescaleDB

Source of truth for the numbers a chart or KPI shows.

  • L2 / L3 marts read via named templates
  • Bucket-stitched time-series for charts
  • Server-side downsampling before the wire

What SDUI actually is

A typed IR (the Component enum in starter-ui-ir), a resolver that turns an authored tree into a renderable tree, and per-platform renderers that walk it. The author never writes JSX, Dart widgets, or CSS.

Author

An operator or the dashboard-assistant AI flow calls rubix.dashboard.create / .update / .page_set with a JSON tree. The tree is stored in Postgres with a revision id.

Resolve

On rubix.dashboard.get the server walks the tree: it pulls data per chart/KPI source, applies bindings, and emits a fully-resolved ComponentTree. The client never sees raw SQL.

Render

React (@nube/starter-ui-sdui-react), Flutter, and Tauri all share the same IR. Each platform ships per-variant renderers — adding a new widget means adding one variant and three renderers.

The component tree, by layer

Every SDUI page is a single root Page node with a tree of layout containers and leaf widgets underneath. The IR enforces what can nest where.

Layout containers

  • Page — the root, owns title + page-level slots
  • Row / Col — flex containers
  • Grid — fixed-column responsive layout
  • Tabs — labelled tab strip
  • Section / Divider — grouping + visual breaks
  • Repeat — fan-out one child template across a list source
  • Drawer / Dialog — overlay surfaces
  • Wizard — multi-step flow shell

Display widgets

  • Text / Heading / Markdown / RichText
  • Badge — status pill with semantic intent
  • Kpi / KpiGrid — scalar numbers with unit + delta
  • Chart — time-series, bar, pie, donut, gauge, area, stacked-bar
  • Sparkline — inline mini-chart
  • Table / ArrayTable / JsonTable
  • List / Tree / Timeline
  • Card / Detail / Diff
  • Menu / ActionWidget

Input widgets (write-path)

  • Form + FieldGroup — grouped multi-field submit
  • TextField / NumberField / Textarea
  • Toggle / Slider / Checkbox
  • Select / SelectField / RadioGroup / Segmented
  • DateField / DateRange
  • RefPicker — pick a node / entity by reference
  • MarkdownEditor
  • Button — fires actions / tools

Two fallback variants exist in every renderer for resilience: Forbidden (ACL-redacted node — surfaces as a stub the user can't see through) and Dangling (a widget the resolver couldn't satisfy, or a V3-only variant reaching a V2 client). Both render as visible placeholders so a missing chart can't crash the page.

Time-series data — how a chart gets its numbers

The author never embeds SQL. They pick a ChartSource variant; the server's resolver does the rest. Six variants today, covering live telemetry, ad-hoc queries, and saved analytics templates.

1 Author picks a source One Chart node names a ChartSource variant and a ChartKind (line, bar, gauge…). No SQL in the tree.
2 Resolver dispatches On dashboard.get the resolver matches the variant and routes to the right backend — domain history, RSQL, or analytics templates.
3 TimescaleDB / RSQL fetch Marts are read through named templates with typed params; bucket-stitched series are built server-side so the browser never sees 100k rows.
4 Downsample + shape The resolver emits a ChartSeries list of [ts_ms, value] points per series, capped to a server-side ceiling.
5 Renderer draws The client gets a ready-to-plot tree. Live updates ride the node.<id>.slot.<slot> binding bus for sources that subscribe.

Series

Time-series over a single node's slot — the V2 default. Live updates stream through the binding bus, so a gauge or line chart tracks the slot in real time without polling.

SeriesByKind

Fans the same slot out across every node of a given kind (e.g. "CPU % per host"). The resolver returns one ChartSeries per node, capped by top_n.

Rows

Categorical RSQL aggregation — count, sum, avg, min, max grouped by a slot field. Powers bar / pie / donut over current state and counter-style KPIs.

SeriesFromRsql

Time-series of an RSQL aggregation. The resolver issues one Rows query per bucket and stitches the results — no write-time rollup needed. Optional group_by emits multi-series.

AnalyticsTemplate

A named SQL template (e.g. meter_value_24h_1m) evaluated through rubix.analytics.query. map.ts_field / map.value_field tells the resolver which columns are time and value.

Static

Server-authored [ts_ms, value] points passed through verbatim. Useful for fixtures, doc charts, and AI-built placeholders before the real data binding is wired.

The data-flow example, end-to-end

The dashboard.data-flow-site-a page (stage 05 of the data-flow scenario) shows two L3 line charts for kWh and litres over the last 24 h, plus an L2 1-minute cross-over chart per meter. The kWh chart binds AnalyticsTemplate{ name: "meter_kwh_last_24h" }; the resolver runs the template against rubix.meter_readings_15m, maps bucket_start → ts_ms and value_avg → series points, and the React renderer draws it. The L2 chart points at meter_value_24h_1m against rubix.meter_readings_1m with the same shape. Same widget, same renderer — only the template changes.

Bindings — the read & write substrate

Bindings are how a widget refers to data outside its own props. They power live updates, two-way controls, and the Repeat fan-out.

Read bindings

Expressions like $target.enabled or $self.value resolve against the page's entity graph. Used by display widgets to pull live slot values; the binding bus pushes updates without re-fetching the tree.

Write bindings (S1)

Toggle, Slider, and form fields carry a BindingSpec naming the slot to write back to, with per-control concurrency (LWW / OCC) and debounce_ms. One control can fan out to many slots in a single submit.

Repeat

Expand one child template across a list source — e.g. one KPI card per meter. The resolver materialises the children with stable synthetic ids so per-row state survives across revisions.

Versioning and forward-compat

Every serde-tagged enum in the IR carries an Unknown fallback so an older client can deserialise a newer tree instead of crashing. The resolver handles the rest.

V3 → V2 downgrade

The resolver knows which ChartKind + ChartSource variants render correctly on V2 clients. Compatible widgets ship inline; V3-only variants are rewritten to Dangling so the user sees a labelled placeholder, not a broken chart.

Custom renderers

ChartKind::Custom("acme.flow_canvas") hands the render off to a registered block renderer. Extensions ship custom chart kinds without touching the core IR.
