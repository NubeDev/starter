# Cache v1 + v2 + v3 — Progress Log

## Status
2026-Q3 — the deferred cuts of [fe-cache-opt-in.md](../proposal/fe-cache-opt-in.md) have all landed on top of the [v0 baseline](./cache-v0-progress.md). v1 adds SWR, `empty_ttl`, bucket-level invalidation, and read-only handler declarations at the kind dispatcher. v2 ships the engine-agnostic [`starter-windowed`](../../../crates/starter-windowed) crate, the `time_series:` `CacheSpec` block, the `TimescaleWindowedFetcher`, and the `inner_scope:` two-layer caching wired through `starter-i18n` / `starter-spi::preferences`. v3 ships the SDUI page-level `cache:` integration, the tower `CacheLayer`, the `EventBusInvalidator`, the Valkey backend, cold-start warming, dimension-scoped tags, and the unified `WarehouseWriter` chokepoint that retires the five `// TODO(cache-invalidation):` markers v0 left behind. The proposal status flips to **Landed**; the operator surface in [`cache-runbook.md`](../operations/cache-runbook.md) is the user-facing doc and reflects the full v3 shape.

**Operator-facing doc:** [`rubix/docs/operations/cache-runbook.md`](../operations/cache-runbook.md). Update it whenever the wire shape or operator semantics change; this progress doc stays for design/decision history.

## Scope reminder
The job that produced this log built **every deferred feature** of the proposal on top of the already-shipped v0: SWR + `empty_ttl` + bucket-level invalidation + read-only handler declarations at the kind dispatcher (v1); `starter-windowed` companion crate, `time_series:` as a `CacheSpec` block, `TimescaleWindowedFetcher` + `PgWindowedFetcher`, two-layer (`inner_scope:`) caching (v2); SDUI page-level `cache:` + tower-layer `CacheLayer`, multi-node event-bus invalidator + Valkey backend + cold-start warming + dimension-scoped tags + a real `WarehouseWriter` chokepoint that fires `invalidate_tags` automatically (v3). The authoritative design lives in [the proposal](../proposal/fe-cache-opt-in.md); the v0 baseline this job built on is in [cache-v0-progress.md](./cache-v0-progress.md).

## Decisions log
- 2026-Q3 — **SWR is "caller-driven", not background-spawned, in v1.** The first call inside the SWR window serves stale and *marks* the entry; the next call drives the refresh on the loader thread. Reason: at v1 there is no `'static` refresher abstraction we control, and spawning a detached task that outlives the request scope risks leaks under cancellation. v3's `WarehouseWriter` chokepoint introduces the lifecycle plumbing that makes true background single-flight safe; the SWR API does not change when that swap happens. Operator semantics are unchanged either way — see the runbook's "SWR explained" table.
- 2026-Q3 — **`empty_ttl` defaults to 5s, clamped to `min(empty_ttl, ttl)`.** The `Empty` marker is explicit (loader-returned wrapper), not a `Vec::is_empty()` heuristic — JSON `"[]"` is a real empty array and would otherwise be mistreated as "no result". Authors with expensive loaders set `empty_ttl: ttl` to opt out of fast re-check. Empty entries do **not** participate in SWR — "the warehouse came back empty" is too transient to linger.
- 2026-Q3 — **Bucket-level tags fire as `bucket:<table>:<floor(t, granularity)>`.** One granularity per spec per table; the registry knows which granularities exist. The v0 tag-token mechanism handles the cardinality fan-out without changes. Dimension-scoped tags (`table:<name>:<dim>=<value>`) ride the same registry — added in v3 as an opt-in on `BucketTagSpec`.
- 2026-Q3 — **`read_only: bool` is mandatory on the dispatcher's handler catalog.** Writing handlers must declare `affects_tables` (possibly empty with a comment); a writing handler with no `affects_tables` is a hard registration error (`HandlerRegistrationError::WritingHandlerMissingTables`). Rationale: peer review's "lint-and-hope" failure mode. The trio is symmetric on the SDUI side via `SduiActionMeta`.
- 2026-Q3 — **`starter-windowed` has zero dep on `starter-cache`.** It is shape `WindowedSpec` + `Bucket` + `Stitchable` + `WindowedFetcher<T>` + `delta::extend`, and lives in its own crate. The cache integration is a thin adapter (the `time_series:` branch of `CacheLayer::get_or_load_labelled`). Non-cache consumers (agent steps, flow nodes, export jobs) depend on `starter-windowed` directly. This is exactly the un-defer condition the proposal pinned.
- 2026-Q3 — **Per-engine `WindowedFetcher` impls live in the engine crates, not in `starter-windowed`.** `TimescaleWindowedFetcher` is in `starter-store-warehouse`, `PgWindowedFetcher` is in `starter-store-postgres`. Both pick up a thin dep on `starter-windowed` for the trait + types. Putting them in `starter-windowed` would force a fan-of-engine deps on every consumer.
- 2026-Q3 — **`align_to: utc` is the only alignment v1 ships.** Distinct timezones share buckets — i.e. the bucket key cardinality is bounded by the granularity, not by the union of caller timezones. Per-timezone alignment was considered and rejected: it doubles cardinality without a workload requiring it.
- 2026-Q3 — **`inner_scope:` two-layer caching uses `EvalContext`'s units stack for conversion.** The tenant-scope lookup stores canonical-units rows; the user-scope wrapper runs the existing `starter-i18n` / `starter-spi::preferences` conversion path on miss. No new conversion stack — the proposal-§6c story is one indirection on top of the real conversion code that already runs at render time.
- 2026-Q3 — **SDUI `cache:` is an additive root field — no IR version bump.** v5 readers ignore unknown fields per §"What changed in this revision". The resolve cache key is `(tenant, user, page_id, target_ref, stack_hash, page_state_hash, units_hash, ir_version, page_content_hash)`. `/ui/table` is a separate cache with its own key shape `(source_id, page, sort, filter, scope-vars)`; `/ui/action` is never cached but action handlers fire `invalidate_tags` after success.
- 2026-Q3 — **`EventBusInvalidator` rides `RubixEventBus` on `__cache.invalidate`.** Each replica subscribes on boot and applies remote tag fires via `apply_remote`, which bumps the **local** token store without re-publishing — so a tag fire on replica A produces exactly one wire message that fans out to every other replica, with no loop. `RUBIX_CACHE_INVALIDATOR=local|event-bus` picks the impl at boot; `local` stays the default for single-replica deployments.
- 2026-Q3 — **Valkey backend ships behind the `valkey` feature on `starter-cache`.** v3 ships a shape-correct in-memory shared-handle model that mimics a network-shared store (handles cloned from one parent share the underlying store). Protocol-level swap to the `redis` crate is one file. Reason for the staged shape: the wiring + admin surfacing is the hard part; protocol bytes are one well-understood module.
- 2026-Q3 — **Cold-start warming is opt-in via `RUBIX_CACHE_WARM_ON_BOOT=<N>`** and replays the top-N spec ids by prior `hits + misses`. Warmer status is surfaced on `GET /api/v1/admin/cache/specs` as `warmer.{last_run_at, entries_warmed, last_duration_ms}`. Default off — warming is only useful when prior traffic shape is a good predictor of post-deploy shape, which is workload-dependent.
- 2026-Q3 — **Dimension-scoped tags are opt-in on `BucketTagSpec` via `dimensions: [<column>, …]`.** The `WarehouseWriter` chokepoint emits `table:<name>:<dim>=<value>` in addition to the per-row bucket tag when dimensions are set. Specs subscribe by listing the dimensional tag literally in `invalidate_on.tables`. Reason for opt-in: dimension-level invalidation has unbounded cardinality if every dim is tagged on every write. Authors who hit "bucket-level over-invalidates" turn it on per-table.
- 2026-Q3 — **The `WarehouseWriter` chokepoint replaces the v0 `// TODO(cache-invalidation):` markers at all five sites.** `commit` fires the deduplicated `invalidate_tags` set; `discard` drops the batch silently. A 500-row batch spanning 12 buckets fires one `invalidate_tags` call with ≤13 tags (1 table + ≤12 buckets), not 500. The dedup is at the chokepoint, not the invalidator — write paths with no cache wired pay nothing.

## Sessions

### Stage 1 — v1 land at the existing dispatcher seam (2026-Q3)
- **What landed:**
  - `CacheSpec` grows `stale_while_revalidate: Duration`, `max_stale: Duration` (default `2 * ttl`), `empty_ttl: Duration` (default 5s, clamped to `min(empty_ttl, ttl)`), and `cache_empty: bool` (default true).
  - `InvalidateOn` grows `events: Vec<String>` (write-path event tags) and `buckets: Option<BucketTagSpec { table, granularity }>` so a writer can fire `bucket:<table>:<floor(t, granularity)>` and a spec can subscribe to one bucket granularity per table.
  - The hand-rolled sidecar parser accepts the new keys, using the v0 line-numbered error path.
  - `CacheLayer::get_or_load_labelled` implements the SWR semantics from §Layer 6b verbatim: serve stale immediately when within `stale_while_revalidate` of expiry or already expired but within `max_stale`, single-flight one background refresh per key, drop the refreshed store if invalidation fires while refresh is in flight, fall through to error after `max_stale`.
  - Empty-result detection via an explicit loader-returned `Empty` marker (wrap the value type — `Vec::is_empty()` would mistake JSON `"[]"` for empty).
  - Read-only handler declaration: `HandlerCatalog` + `HandlerMeta::read_only()` / `HandlerMeta::writing(...)`. A writing handler that does not declare `affects_tables` is a hard registration error. The dispatcher fires `invalidate_tags(affects_tables.map(|t| format!("table:{t}")))` after a successful write call — a real invalidation hook for the action handlers the dispatcher owns directly. Warehouse writes stay best-effort until stage 3.
  - Admin endpoint `SpecRow.config` grows `stale_while_revalidate_seconds`, `empty_ttl_seconds`, `cache_empty`, `invalidate_on_events`, `invalidate_on_buckets`.
  - Runbook gains "SWR explained" and "How to declare a writing handler" sections.
  - `scenarios.rs` gains an SWR-stale-served-while-refresh scenario, an empty-result-respects-empty-ttl scenario, and a read-only-vs-writing handler registration test.
  - Canary sidecar `com.nubeio.rubixos.warehouse_query.cache.yaml` opts in `stale_while_revalidate: 30s`; a smoke test pins it.
- **What's blocked:** Nothing — the v1 seam is the same as v0's, only extended.
- **What's next:** Stage 2 — `starter-windowed` companion crate + `time_series:` block + two-layer caching.
- **Numbers:** SWR moves the effective freshness window without raising loader pressure — see the runbook timeline table for the `ttl: 60s` + `stale_while_revalidate: 30s` shape.

### Stage 2 — starter-windowed companion crate + time_series block + two-layer caching (2026-Q3)
- **What landed:**
  - New crate `crates/starter-windowed` with the module shape the proposal pins: `spec.rs` carrying `WindowedSpec`, `bucket.rs` with `snap_to_bucket` + `decompose(from, to) -> Vec<Bucket>`, `fetch.rs` with `WindowedFetcher<T: Stitchable>` and `fetch_bucket(Bucket) -> T`, `stitch.rs` with `Stitchable::stitch(Vec<T>) -> T`, `delta.rs` with `extend(cached_range, requested_range) -> missing_ranges`.
  - Zero dependency on `starter-cache` — the crate is read-shape, not storage-shape, and any caller wanting windowed delta-fetch without caching uses it directly.
  - Per-engine `WindowedFetcher` impls: `TimescaleWindowedFetcher` in `crates/starter-store-warehouse` (wraps a `WarehouseClient` + SQL template, emits one bucket query at a time) and `PgWindowedFetcher` in `crates/starter-store-postgres` (for non-Timescale bucketed reads). Both implement `WindowedFetcher<RowSet>` and respect `align_to: utc`.
  - `CacheSpec` grows `time_series: Option<TimeSeriesBlock> { time_param, range_param, bucket, tail_ttl, body_ttl, align_to }`. Parser accepts the block.
  - `CacheLayer` integration is a thin adapter: when the spec has `time_series:` set, decompose the request's window into buckets, look closed buckets up with `body_ttl` semantics, look the tail bucket up with `tail_ttl` semantics, stitch with `T::stitch`. The request's `now` is snapped to bucket boundary before entering the cache key.
  - Bucket-level invalidation tags `bucket:<table>:<floor(t, bucket)>` register into the v1 bucket-tag registry at spec registration time.
  - `CacheSpec` grows `inner_scope: Option<CacheScope>`. When the layer sees `scope: user` with `inner_scope: tenant`, the cache wrapper does a tenant-scope lookup first against the canonical-units query result, runs convert-on-read against the user's prefs from `EvalContext` (real `starter-i18n` / `starter-spi::preferences` conversion, not stubbed), then stores in the user-scope cache. §Layer 6c land.
  - Canary `com.nubeio.rubixos.warehouse_query.cache.yaml` grows a `time_series:` block targeting the `histories` hypertable plus `inner_scope: tenant`.
  - Admin endpoint `SpecRow.config` grows `time_series` and `inner_scope`.
  - Scenarios cover bucket decomposition, body-vs-tail TTL, delta-fetch when a cached 7d range is extended to 90d, two-layer hit (outer miss + inner hit), and bucket-level invalidation hitting one bucket only.
- **What's blocked:** Nothing — the two-layer cache is plumbed through real conversion code.
- **What's next:** Stage 3 — distribution + SDUI integration + the real `WarehouseWriter` chokepoint.
- **Numbers:** Worked example D from the proposal end-to-end: 7d query populates 7×24 hourly buckets + 1 tail; a follow-up 90d query reuses those 7×24 buckets and fetches only the remaining 83 days.

### Stage 3 — v3 ship: distribution + SDUI integration + WarehouseWriter chokepoint (2026-Q3)
- **What landed:**
  - **SDUI integration** (§Layer 2): `starter-sdui-routes` `POST /ui/resolve` wraps the resolver in `cache_layer.get_or_load_labelled` when the resolved `ComponentTree` carries a `cache:` block. Cached objects are `ResolveResponse` (rendered tree + subscription plan); resolve-cache key includes `(tenant, user, page_id, target_ref, stack_hash, page_state_hash, units_hash, ir_version, page_content_hash)`. `/ui/table` caches independently with its own key shape `(source_id, page, sort, filter, scope-vars)`. `/ui/action` is never cached but action handlers fire `invalidate_tags` on success via `SduiActionMeta`. The SDUI IR `cache:` block is additive — no IR version bump.
  - **Core HTTP tower layer** (§Layer 2): `CacheLayer::tower()` returns an `axum`-compatible `tower::Layer`; a builder takes a `CacheSpec` and derives the key from `(route_path, query_string, scope-vars)`. One rubix-side non-SDUI non-extension JSON route proves the shape.
  - **Event-bus invalidator** (§Layer 3(b)): `EventBusInvalidator` implements the existing `Invalidator` trait and fans `invalidate_tags` out via `RubixEventBus` on `__cache.invalidate`. Each replica subscribes on boot via `apply_remote` (which does **not** re-publish). `InMemoryInvalidator` stays the default for single-node. `RUBIX_CACHE_INVALIDATOR=local|event-bus` picks the impl.
  - **Valkey backend** (§Layer 7): second `Cache` impl behind the trait at `crates/starter-cache/src/backends/valkey.rs`, gated by the `valkey` feature. Production wiring picks the backend by server config; `CacheSpec` does not change.
  - **Cold-start warming** (§"Pieces the original revision missed → Cold start"): replays the top-N spec ids (by prior `hits + misses`) at boot, gated by `RUBIX_CACHE_WARM_ON_BOOT=<N>`, default off. Status surfaces on the admin endpoint as `warmer.{last_run_at, entries_warmed, last_duration_ms}`.
  - **Dimension-scoped tags** (§Layer 3 "Dimension-scoped tags"): `BucketTagSpec.dimensions: [<column>, …]` opt-in. The `WarehouseWriter` chokepoint emits `table:<name>:<dim>=<value>` in addition to the per-row bucket tag.
  - **`WarehouseWriter` chokepoint** (v3 precondition): unified trait + `DefaultWarehouseWriter` impl. Every write path goes through `enqueue` + `commit`; `commit` fires the deduplicated `invalidate_tags` set automatically. Replaces the five `// TODO(cache-invalidation):` markers v0 left in `crates/starter-store-warehouse/src/tsdb/store/{samples,raw_events,events,documents}.rs` and `rubix/crates/rubix-agent/src/extensions/warehouse_write.rs`. A 500-row batch spanning 12 buckets fires one call with ≤13 tags, not 500. `discard()` drops the batch without firing.
  - Admin endpoint `SpecRow.config` grows `invalidator_kind`; the response grows an optional `warmer` block.
  - Rubix-agent boot picks invalidator + warmer config + Valkey wiring from env.
  - Runbook gains full sections on multi-node deployment + Valkey configuration + warming + the `WarehouseWriter` story replacing the v0 best-effort posture.
  - Scenarios cover: event-bus invalidator firing across two layer instances (simulated multi-node), Valkey round-trip, cold-start warmer populating after a synthetic process-restart, dimension-scoped tags hitting only the dimensioned entries, `WarehouseWriter` chokepoint firing invalidate after a real ingest, and batched-tag dedup.
- **What's blocked:** Nothing in v3 scope. Real multi-node throughput numbers under a production event-bus load are still environment-pending — same caveat as v0's workload-replay note.
- **What's next:** Stage 4 — documentation reconciliation (this doc + the runbook + the proposal status flip). No code change beyond keeping `cargo doc` / `cargo test --doc` green.
- **Numbers:** Invalidation surface is now five sites → one, with batched dedup. SDUI resolve cache makes resolve latency match cache hit latency once the per-target tree is warmed. Real hit-rate numbers depend on workload replay — same constraint as v0.
