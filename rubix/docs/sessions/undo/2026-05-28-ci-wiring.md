## What landed

A new `undo-postgres` job in [`.github/workflows/ci.yml`](../../../../.github/workflows/ci.yml)
that runs the two `#[ignore = "requires docker"]` integration tests on every
PR / push:

1. `cargo test -p starter-undo --features postgres --test cursor_postgres -- --ignored --test-threads=1`
   — five tests covering the `PgUndoCursor` epoch CAS path (round-trip,
   isolation, persistence, concurrent CAS, agent-run-id keying).
2. `cargo test -p rubix-agent --test undo_redo_e2e_test -- --ignored`
   — end-to-end: create + update + undo + redo + clear-on-mutation
   + cross-process replay against testcontainers Postgres.

Both already pass locally with the docker daemon up. The job mirrors the
shape of the existing `test (starter-store-postgres, testing feature,
--ignored)` step in the main `rust` job — GitHub-hosted `ubuntu-latest`
provides docker by default, so no service-container scaffolding is
needed; `testcontainers` brings up its own ephemeral Postgres
(`17-alpine`, pinned in
[`starter-store-postgres::testing::with_database`](../../../../crates/starter-store-postgres/src/testing/with_database.rs)).

### Decision: separate job, not a step in `rust`

I considered tacking the two `cargo test … --ignored` lines onto the
existing `rust` job. Split into its own `undo-postgres` job instead so:

- Cache key stays distinct from the workspace step that's already
  doing fmt / clippy / test — failure surface is unambiguous in the
  PR check list ("did undo regress, or did the workspace?").
- The undo path can grow more docker-backed suites (admin-side
  policy verb, future warehouse Reversibles) under one job without
  bloating the main rust step.

## Also landed this session: audit-log proposal (unblocks §3.3)

New proposal at
[`rubix/docs/proposal/audit-log.md`](../../proposal/audit-log.md).
Closes the §3.3 prerequisite that the prior session called out as
"ship the audit-log proposal FIRST, don't extend undo retention to
substitute for audit."

Recommendation in the proposal: **don't build a new audit system.**
The ingredients all exist —

- `starter-changelog` is the write path (every `Reversible` mutation
  already lands a `Change` row in `starter_changes`).
- `starter-audit` is the visibility-gated read projection at
  `GET /v1/audit` over `starter_changes`.
- `starter-authz::audit` is the (separate) decision audit.

Critical clarification surfaced while writing the proposal: the
rubix undo sweep
([`undo_sweep.rs`](../../crates/rubix-agent/src/boot/undo_sweep.rs))
prunes `undo_snapshots`, **not** `starter_changes`. The two tables
are distinct: `undo_snapshots` is the operational record (replay
buffer for `rubix.undo.last`); `starter_changes` is the historical
record (read by `starter-audit`) and has **no rubix-side sweep
today** — effectively unbounded.

So the §3.3 "undo retention destroys audit" concern is already
structurally avoided. Pruning the snapshot table only loses the
*undo capability*, not the audit row.

The actual gaps for §3.3 are narrower than the parent proposal
implied:

1. Role / prefs / tenant_id writes don't flow through any rubix verb
   yet, so no `Change` row gets produced for them — *the audit
   table is fine; the producer is missing*.
2. There's no per-kind policy declaring "this kind must never be
   pruned." Today retention is implicit-unbounded by absence of a
   sweep; the proposal adds an explicit `changelog_kind_policy`
   table so security-relevant kinds (`user`, `team`) carry the
   intent in SQL.
3. No frontend audit page yet (out of scope).

Concrete next-step list lives at the bottom of the proposal.

## Also landed this session: step 1 + 2 of the audit-log proposal

Closes proposal "Concrete next steps" #1 and #2 — the schema +
helper land together because the migration is useless without the

### Schema

New migration
[`crates/starter-changelog-postgres/migrations/0004_changelog_kind_policy.sql`](../../../../crates/starter-changelog-postgres/migrations/0004_changelog_kind_policy.sql):

```sql
CREATE TABLE changelog_kind_policy (
    resource_kind TEXT        PRIMARY KEY,
    max_age_days  INT,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

Three states an operator can express:

- No row → no policy → no automatic prune (today's behaviour;
  nothing surprises an operator who hasn't opted in).
- Row with `max_age_days = NULL` → explicit "keep forever." Used
  for security-relevant kinds so the audit floor is recorded in
  SQL, not in tribal memory.
- Row with `max_age_days = N` → operator opted into bounded
  retention for that kind.

### Helper

New module
[`crates/starter-changelog-postgres/src/policy.rs`](../../../../crates/starter-changelog-postgres/src/policy.rs):
`apply_policy(pool) -> Result<PolicyReport>`. One `DELETE` per
kind that has `max_age_days IS NOT NULL`. Kinds with no row or a
NULL curve are skipped entirely — opting in is always explicit.
`PolicyReport::per_kind` carries `(kind, rows_deleted)` for the
caller (future boot sweep) to log.

Re-exported from the crate root as `apply_policy` and
`PolicyReport` so consumers don't need to know the module layout.

### Tests

[`crates/starter-changelog-postgres/tests/policy.rs`](../../../../crates/starter-changelog-postgres/tests/policy.rs)
— four `#[ignore = "requires docker"]` tests pinning the contract:

1. `no_policy_rows_means_no_deletes` — implicit-unbounded today's
   behaviour is preserved.
2. `null_max_age_pins_kind_to_unbounded` — the audit-floor marker
   works.
3. `finite_max_age_deletes_older_rows` — boundary at exactly the
   curve, drops older.
4. `policy_is_per_kind_does_not_touch_unlisted_kinds` — pins the
   isolation contract; a sweep for `flow_def` cannot collateral-
   damage rows from `user`. Load-bearing for the audit-floor story.

Verified locally: `cargo test -p starter-changelog-postgres --test policy
-- --ignored --test-threads=1` → `4 passed; 0 failed` in 6.5s.

### Boot module

[`rubix-agent/src/boot/changelog_sweep.rs`](../../../crates/rubix-agent/src/boot/changelog_sweep.rs)
— mirror of [`undo_sweep.rs`](../../../crates/rubix-agent/src/boot/undo_sweep.rs)
targeting `starter_changes` rather than `undo_snapshots`. Boot-tick
runs inline (so a fresh deploy sees the curve applied before traffic
hits), then a 24h ticker until the returned `JoinHandle` is dropped.
`Option<JoinHandle<()>>` return so the laptop / no-PG path stays
quiet (matches every other sweep in `boot/`).

Spawned from
[`rubix-agent/src/main.rs`](../../../crates/rubix-agent/src/main.rs)
next to `_undo_sweep`. The two sweeps are deliberately separate
tasks: they read different policy tables, sweep different target
tables, and a stuck one cannot stall the other.

### Migration source

[`rubix-store-postgres/migrations/changelog_policy/0001_audit_floor_seed.sql`](../../../crates/rubix-store-postgres/migrations/changelog_policy/0001_audit_floor_seed.sql)
— `INSERT … ON CONFLICT DO NOTHING` for `user` and `team`, both with
`max_age_days = NULL`. The intent is recorded in SQL so a future
operator who adds finite retention for chatty kinds can't accidentally
prune the security-relevant trail.

Exposed as `CHANGELOG_POLICY_MIGRATION_SOURCE` from
[`rubix-store-postgres/src/lib.rs`](../../../crates/rubix-store-postgres/src/lib.rs)
following the same `MigrationSource` pattern as `UNDO_SNAPSHOTS_…`
and `FLOWS_DEFINITIONS_…`. Each source carries its own
`_sqlx_migrations_<name>` table so re-runs are independent.

Chained into [`boot/migrations.rs`](../../../crates/rubix-agent/src/boot/migrations.rs)
immediately after the upstream `changelog` source — ordering matters
because the seed INSERTs target a table the upstream source
provisions.

### Why not co-locate the seed with the changelog migrations

The `changelog_kind_policy` table is generic (lives in
`starter-changelog-postgres`). The seeded kinds (`user`, `team`) are
rubix-domain concepts. Putting the rubix seed inside the generic
crate would couple `starter-changelog` to rubix vocabulary — wrong
layering. A new `migrations/changelog_policy/` dir under
`rubix-store-postgres` keeps the seed where its semantics belong.

### Tests

[`rubix-agent/tests/changelog_sweep_test.rs`](../../../crates/rubix-agent/tests/changelog_sweep_test.rs)

1. `seed_lands_user_and_team_as_audit_floor` — runs the migration
