## Design decisions

### Why the sink receives *resolved* connection material (not the raw datasource id)

`nexus-engine` has no `nexus-store` dependency and must not gain one (it sits below the
store-coupled api; the existing `PostgresSink` already takes a pre-decrypted `uri` — see
its doc: "decrypted by the caller at build time"). So the secret resolution (fetch record,
decrypt via the audited `open_secret`, build conn string) stays in `nexus-store` /
`nexus-api`, and the engine sink is handed a resolved config. This keeps the layering
(`engine → spi`, never `engine → store`) intact and reuses the exact audited decrypt path
the query side uses.

Resolution flow:
`routes/flows/start.rs` → `datasource_kinds::resolve_flow_output` (nexus-api, my lane)
→ `nexus_store::datasource::resolve_sink_conn` (audited decrypt, my lane append)
→ rewrites `{datasource:id,table,...}` into the engine's resolved `datasource` sink config.

### COPY writer choice: sqlx PgCopyIn (text format), not tokio-postgres BinaryCopyInWriter

Spec asked to spike both. Chose **sqlx `PgCopyIn` + `COPY ... FROM STDIN (FORMAT text)`**:
- sqlx is already the workspace driver; tokio-postgres would be a *second* Postgres client
  stack — exactly the bloat ROADMAP §8 warns against ("no second Postgres client stack").
- Text COPY can carry every JSON-derived scalar via its text representation (NULL/bool/
  int/float/string), so no type needs the multi-row-INSERT fallback for the shapes the
  Arrow→JSON bridge produces. Non-scalars round-trip as JSON text, same rule the old
  `pg_insert` used.
- I own the COPY encoding (escaping tab/newline/backslash/`\N`), which is small and
  self-contained in `postgres_copy.rs`.
- `PgCopyIn::finish()` is always called (on flush) to complete the COPY; an aborted batch
  calls `abort()`.

### File writer: Parquet via `datafusion::parquet::arrow::AsyncArrowWriter`

parquet 55.2.0 + object_store 0.12.5 are already resolved (transitive via datafusion 47;
datafusion re-exports `parquet`). Both are §8-approved. Local-fs first: writes a rotating
part-file with `AsyncArrowWriter` over a `tokio::fs::File`. Rotation on SIZE (≥64MB) OR
ROWS, never the generic batch timer — timer-flushed tiny row groups are the small-files
problem the spec calls out. S3 via object_store is config-accepted but feature-gated OFF
(`s3` feature), so the default build pulls no S3 client.

### No migration

Datasource records + envelope-sealed secrets already exist (WS-08b). RW-04 adds no column
or table, so the reserved `20xx` block is left unused. (Confirms spec point 5.)

## Task breakdown executed

1. `nexus-engine/src/sink/datasource/` (new folder, verb/concept-per-file):
   - `writer.rs` — `DatasourceWriter` trait (`write_batch` + `flush`).
   - `identifier.rs` — strict allowlisted-shape identifier guard (mirrors the query
     binder's `validate_identifier`); table + every JSON-derived column validated before
     it reaches SQL text.
   - `postgres_copy.rs` — `PgCopyIn` text-COPY writer; owns COPY text escaping.
   - `parquet_file.rs` — `AsyncArrowWriter` rotating part-files on size (≥64MB) OR rows,
     never the batch timer; local-fs first, S3 deferred behind a future feature.
   - `batch.rs` — `BatchAccumulator`: flush on `batch_rows` OR `batch_ms`, `concat_batches`
     on drain; unit-tested under paused tokio time.
   - `mod.rs` — `DatasourceSink`: parses resolved config, batches, dispatches to the
     kind's writer (lazy-opened on first write so the registry builder stays sync), flushes
     the tail on close.
2. Registered `datasource` in `native_registry.rs` + `sink/mod.rs` re-export.
3. `nexus-store/src/datasource/resolve.rs` (append) — `resolve_sink_config`: fetch record,
   audited `open_secret`, emit the engine sink config `Value` with discrete conn fields
   (no URI percent-encoding fragility).
4. `nexus-api/src/datasource_kinds/resolve_output.rs` (append) — `resolve_flow_output`:
   rewrites a `{type:datasource, datasource:id, table}` output into the resolved config;
   other outputs pass through unchanged (legacy flows untouched).
5. `nexus-api/src/routes/flows/start.rs` — thin transport seam: resolve the output before
   `flows.start` (one extract→call-domain→map append; no logic).
6. Tests: batch/identifier/copy unit tests (in-crate); `sink_datasource` (row-count +
   close-tail batching, Parquet read-back via DataFusion); `sink_datasource_registry`
   (legacy postgres + new datasource configs both build); `routes_datasources_sink_e2e`
   (docker-gated full flow → datasource COPY, both rows land, decrypt audit via open_secret).

## Assumptions / follow-ups

- COPY writer is `sqlx::PgCopyIn` text format; no tokio-postgres (§8 second-client-stack
  avoidance). Text COPY carries every Arrow→JSON scalar, so the multi-row-INSERT fallback
  was not needed for the produced shapes.
- S3/object_store backend is deferred behind a future `s3` feature; local-fs Parquet uses a
  tokio `File` directly (parquet's blanket `AsyncFileWriter for AsyncWrite`), pulling no S3
  client into the default build.
- Follow-up logged to TODOs.md: the `datasource` sink lacks a flow-builder palette
  descriptor (that table lives in RW-03's `registry/` lane). The sink is fully functional
  via raw config; only the visual palette entry is missing.
